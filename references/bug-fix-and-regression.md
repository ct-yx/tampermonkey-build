# Bug 修复、回归与发布前检查

## 诊断闭环

先建立一个能对用户症状判红的命令、脚本或浏览器采样：例如几何变化计数、缺失卡片数量、网络失败率、重复初始化次数或刷新完成时间。不能只用“页面没报错”作为测试。

对于不稳定 Bug，按问题风险选取足够的验证项，不要求每个任务都执行完整组合矩阵：

1. 固定 URL、窗口、缓存/登录状态和操作步骤。
2. 记录 3–5 个可证伪假设并排序。
3. 每次只改变一个变量，优先禁用可疑 observer、patch、预加载或重试。
4. 缩小到最小仍失败的场景。
5. 在正确的边界写回归测试；如果没有合适边界，记录缺口而不是制造假测试。
6. 修复后同时跑最小复现和原始用户场景。

## userscript 行为测试与页面回归

让测试经过稳定的模块/API 边界，优先覆盖这次修改可能影响的场景，例如：

- 首次打开、普通刷新、强制刷新、返回/前进。
- SPA 路由切换和重复进入同一路由。
- 首屏、滚动加载、悬停预览、窗口缩放。
- 图片成功、单资源失败、CDN 节点失败、网络离线再恢复。
- 顶层页面、同域 iframe、跨域 iframe（若适用）。
- Tampermonkey 与 Violentmonkey；Chrome/Edge 与 Firefox（仅在项目声明支持时）。
- 脚本重复注入、Tampermonkey 权限拒绝和旧版本存储数据（仅在相关时）。
- 页面作用域：目标模块只在声明的页面类型运行；数据格式或请求协议不同的页面族分别使用匹配的解析器和请求处理；SPA 离开旧路由后监听器、请求和缓存被清理。

纯逻辑使用可直接调用的函数测试；DOM/GM API 行为通过 mock 或小型 adapter seam 测试；最终在 Edge + Tampermonkey 实测用户路径。不要为了测试而用 `indexOf`/`slice` 从大文件中截取函数体，这种测试容易与源码结构耦合且不能反映模块行为。

## 开发完成后的发布前检查

```bash
python3 <SKILL_DIR>/scripts/validate_userscript.py path/to/script.user.js
node --check path/to/script.user.js
```

这些检查属于 userscript 发布模式，不会自动发布。另运行项目测试和 `git diff --check`。若通过 Raw 地址更新，项目根目录必须有由源码生成的 `.user.js`，其 `@updateURL` 和 `@downloadURL` 应指向有效地址；构建产物不可手动编辑。确认 metadata 版本递增、构建产物只有一个 metadata block、无临时调试日志/本地 URL/测试开关、许可证和第三方归属齐全。记录真实验证的浏览器、管理器版本、日期和未验证项目；下载/导入模式不使用这一步替代来源审查。

## 回滚

每次修改已安装脚本前保存原文和时间戳；MCP patch 使用最后修改时间或等价的乐观锁。线上失败时先停止扩展范围，恢复备份并验证恢复版本，不自动删除用户数据或重置整个脚本库。

## 信息流类性能 Bug 的验收

“频闪”不能只看截图：同时采样卡片几何变化、class/style mutation、直接子节点变化和脚本统计。若用户要求不修改预览内容，就把预览 DOM 和资源 URL 列入不变性断言。
