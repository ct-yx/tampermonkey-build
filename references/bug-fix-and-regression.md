# Bug 修复、回归与发布前检查

## 诊断闭环

先建立一个能对用户症状判红的命令、脚本或浏览器采样：例如几何变化计数、缺失卡片数量、网络失败率、重复初始化次数或刷新完成时间。不能只用“页面没报错”作为测试。

对于不稳定 Bug：

1. 固定 URL、窗口、缓存/登录状态和操作步骤。
2. 记录 3–5 个可证伪假设并排序。
3. 每次只改变一个变量，优先禁用可疑 observer、patch、预加载或重试。
4. 缩小到最小仍失败的场景。
5. 在正确的边界写回归测试；如果没有合适边界，记录缺口而不是制造假测试。
6. 修复后同时跑最小复现和原始用户场景。

## 回归矩阵

至少覆盖与功能有关的组合：

- 首次打开、普通刷新、强制刷新、返回/前进。
- SPA 路由切换和重复进入同一路由。
- 首屏、滚动加载、悬停预览、窗口缩放。
- 图片成功、单资源失败、CDN 节点失败、网络离线再恢复。
- 顶层页面、同域 iframe、跨域 iframe（若适用）。
- Tampermonkey 与 Violentmonkey；Chrome/Edge 与 Firefox（若声明支持）。
- 脚本重复注入、扩展拦截、用户拒绝权限和旧版本存储数据。

## 开发完成后的发布前检查

```bash
python3 <SKILL_DIR>/scripts/validate_userscript.py path/to/script.user.js
node --check path/to/script.user.js
```

这些检查属于发布模式，不会自动发布。确认 metadata 版本递增、更新地址可访问、构建产物只有一个 metadata block、无临时调试日志/本地 URL/测试开关、许可证和第三方归属齐全。记录真实验证的浏览器、管理器版本、日期和未验证项目；下载/导入模式不使用这一步替代来源审查。

## 回滚

每次修改已安装脚本前保存原文和时间戳；MCP patch 使用最后修改时间或等价的乐观锁。线上失败时先停止扩展范围，恢复备份并验证恢复版本，不自动删除用户数据或重置整个脚本库。

## 信息流类性能 Bug 的验收

“频闪”不能只看截图：同时采样卡片几何变化、class/style mutation、直接子节点变化和脚本统计。若用户要求不修改预览内容，就把预览 DOM 和资源 URL 列入不变性断言。
